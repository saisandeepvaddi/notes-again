# Notes Again

Personal, self-hosted spaced-repetition app: freeform markdown notes organized into projects and tags, resurfaced for review on an SM2/FSRS schedule. Single user per deployment.

- Current status, owner rules and next steps for a new agent: [docs/handoff.md](docs/handoff.md)
- Product-development checklist (writing safety, article clipping, BYOK chat and connected notes): [docs/plans/knowledge-workflow.md](docs/plans/knowledge-workflow.md). Update its checkboxes as work lands; platform parity remains in [docs/plans/cross-platform.md](docs/plans/cross-platform.md).
- Product intent and audience: [PRODUCT.md](PRODUCT.md)
- Visual system (colors, type, components): [DESIGN.md](DESIGN.md)
- Running and self-hosting (make run, install.sh, Docker, sign-in, backups): [docs/self-hosting.md](docs/self-hosting.md)
- Brand icons: `assets/` holds the source artwork. `node scripts/build-icons.mjs` (uses the frontend's Playwright Chromium) renders every platform variant into `frontend/public/`, `extension/public/icon/` and `mobile/assets/images/`; edit the sources and rerun rather than editing the generated files.
- `README.md` is the public overview; `install.sh` is the guided Docker installer (POSIX sh, test changes under `dash`).

## Layout

- `server/`: Rust (axum + sqlx on SQLite), one crate built as both a library and the `notes-again-server` binary. One module per domain (`notes`, `groups` for tags/projects/settings, `imports`, `search`, `sync`, `auth`, `system`, `backups`), mounted under `/api` behind `auth::require_user` in `app.rs`. The binary is the server (`serve`) and the maintenance CLI.
- `frontend/`: TanStack Start in SPA mode (built to static files, served by the Rust server in production), TanStack Router file routes, TanStack Query, shadcn on Base UI (not Radix), Tailwind v4, Zod v4. Before editing TanStack code, run the matching guidance command listed in [frontend/AGENTS.md](frontend/AGENTS.md).
- `desktop/`: Tauri 2 desktop app that links the `server` crate and runs it in-process (`start_desktop`, `AUTH_MODE=desktop`) on `127.0.0.1`, so it works with no server. Its own pnpm root; see [desktop/README.md](desktop/README.md).
- `extension/`: WXT browser extension for capture. It is its own pnpm root; see [extension/README.md](extension/README.md).
- `mobile/`: Expo (React Native) app with the full feature set, its own pnpm root. It embeds the Rust server like the desktop app (`mobile/modules/notes-core`), keeps its notes on the phone and syncs through the desktop sync endpoints; it needs a development build, not Expo Go. It imports pure modules from `frontend/src` through the `@web/*` alias (Zod schemas, rating/difficulty options, `markdownExcerpt`, the QR sign-in link format in `settings/api-tokens/connectLink.ts`), so those files must stay free of `@/` imports and DOM or web-only dependencies. See [mobile/AGENTS.md](mobile/AGENTS.md).

## Running locally

- As a user would: `make run` builds the SPA and serves it from the backend via `scripts/serve.sh`, which ignores shell auth/DB/port variables and reads `.env.local` instead (defaults 127.0.0.1:8000, local sign-in; `make run DB=...` for a throwaway database).
- Server: `make dev-server` (`cargo run -- serve` in `server/` with `AUTH_DISABLED=1 CORS_ORIGINS=http://localhost:5273`); rerun it after Rust changes. The repo-root `.env` holds container/production values (`DB_PATH=/data/...`, secrets); keep it out of local runs. With `DB_PATH` unset, the DB lives in the OS app-data dir (`~/Library/Application Support/notes-again/` on macOS).
- Frontend: `pnpm dev` in `frontend/` (port 5273). The API defaults to the host you opened the app on, port 8000; `VITE_SERVER_IP`/`VITE_SERVER_PORT` in an optional `frontend/.env` override it. A stale `VITE_SERVER_IP` (an old LAN address) is the usual cause of a forever-spinning UI: requests time out after 10s with an error naming the address they tried. The login screen follows whatever auth mode the backend reports at `/api/auth/status`, so `AUTH_DISABLED=1` on the backend means no login in dev.

## Verifying changes

- Frontend: `pnpm typecheck`, `pnpm lint` (oxlint), `pnpm test` (vitest unit tests in `frontend/tests/` for pure modules; keep UI flows in E2E).
- Server: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` (from `server/`), or `make check-server test-server`. API behaviour is tested in `server/tests/` through `tests/common` (`TestApp` drives the real router in-process on a temp DB, `TestApp::with` adjusts the `Config`, `serve()` puts it on a real port for sync tests); Firebase and Cloudflare Access tests sign real RS256 tokens with keys from `tests/common/jwt.rs`. Pure logic keeps unit tests next to the code. `tests/perf.rs` is an opt-in budget check with 10,000 notes (list, due, search, ids, a first sync and idle syncs): `cargo test --release --test perf -- --ignored --nocapture`.
- Extension: `pnpm typecheck`, `pnpm test`.
- Desktop: `cargo build` and `cargo fmt` in `desktop/src-tauri`; `pnpm dev` to run it against the repo's SPA build.
- Mobile: `pnpm typecheck`, `pnpm lint` (oxlint), `pnpm doctor` after dependency changes.
- E2E: `make test-e2e`. Playwright starts its own server via `cargo run` (8210) and frontend (5290) on a throwaway DB. With `E2E_BUILT=1` it skips Vite and has the server serve `frontend/dist/client` (build it with `VITE_SERVER_IP=127.0.0.1 VITE_SERVER_PORT=8210`); CI runs it that way. Specs share that DB and run serially, so seed data with `uniqueName()` from `e2e/support/api.ts`. The first run on a cold Vite server is slow and can time out once.
- The formatters (oxfmt; `cargo fmt` is applied to Rust) have never been applied repo-wide. Run them only on files you touch, so diffs stay limited to your change.

## Conventions

- Code carries no comments. Tool directives stay because they change behaviour: `eslint-disable`, `@ts-*`, `/// <reference>`, `// @vitest-environment`, `#[allow(...)]`.
- Schema changes: add a new numbered file in `server/migrations/` (sqlx migrations, embedded at compile time). Indexes, triggers and the search table live in `server/src/db/ensure.sql`, which runs idempotently on every startup. `LEGACY_COLUMNS` in `server/src/db/mod.rs` upgrades databases created by the old Python backend; don't add to it. Datetimes are stored as `YYYY-MM-DD HH:MM:SS.ffffff` UTC text (`time::Ts`) because SQL compares them as strings.
- Single user: rows default to `user_id=1`.
- Backups: `server/src/backups.rs` takes `VACUUM INTO` snapshots on a schedule started by `prepare` in `lib.rs` (`BACKUP_INTERVAL_HOURS=0` turns it off). Maintenance commands are subcommands of the binary in `server/src/main.rs` (`reset-login`, `snapshot`, `restore`, `doctor`, `reindex`, `healthcheck`).
- Search: `notes_fts` is an FTS5 trigram index over `notes.name`/`notes.content`, kept in sync by SQLite triggers in `server/src/db/ensure.sql` (the table is rebuilt at startup if missing), so any write path stays indexed without app code. Both `/api/search` and the notes list `search` param match through `server/src/search.rs`.
- Auth: `AUTH_MODE` is `local` (default; username/password in the `local_auth` table, HttpOnly session cookie backed by `auth_sessions`), `firebase` (runtime web config from `VITE_FIREBASE_*` on the server; ID tokens are verified against Google's public keys, with the project from `FIREBASE_CREDENTIALS_FILE`), `proxy` (username header, trusted only from `TRUSTED_PROXIES`), `cloudflare-access` (verifies the Access JWT; `auth/external.rs`), `desktop` (only the desktop app's window, via a per-launch `DESKTOP_SECRET` cookie), or `none`. `ALLOWED_EMAILS` applies to firebase, proxy and cloudflare-access. `auth/request.rs` records the real peer and applies `X-Forwarded-*` only from `TRUSTED_PROXIES`. Firebase needs an explicit `AUTH_MODE=firebase`; unset `AUTH_MODE` means `local`, or `none` with `AUTH_DISABLED=1`. In local mode the owner can also turn login off from the UI. `/api/auth/*` is public; everything else under `/api` goes through `require_user`. Firebase setup lives in [docs/firebase-auth.md](docs/firebase-auth.md).
- API tokens are scoped. The extension's `capture` tokens can only list/create projects and tags and create notes. `app` tokens (the mobile app) can call everything except token management and `/api/system`, which `Identity::require_session` keeps to real sessions. In local mode `POST /api/auth/token` trades a username and password for an `app` token, and `DELETE /api/auth/token` revokes the caller's own token.
- Note Markdown: `GET /api/notes/{id}/markdown` (`server/src/notes/markdown.rs`) is the single builder for "Copy as Markdown", "Download as Markdown" (`?download=1`) and agents using an `app` token. It emits YAML frontmatter (quoted with JSON strings so any title stays valid YAML), the title as H1 and the body verbatim; a note's own frontmatter is merged in and wins on conflicts. Browsers only see `Content-Disposition` cross-origin because CORS exposes it in `app.rs`.
- Sync: notes, projects, tags and settings carry a `uid` (stable across devices) and a `sync_version` that SQLite triggers in `server/src/db/ensure.sql` bump on every write, with hard deletes recorded in `sync_tombstones`, so any write path is tracked without app code. Difficulty tags use fixed uids (`difficulty-easy` etc.). The server side is `/api/sync/push` and `/api/sync/pull` (`sync/server.rs`); the desktop runs `sync/client.rs`, which keeps each row's last-synced payload in `sync_bases` so the server can three-way merge (`sync/merge.rs`). Text edits on both sides become rows in `sync_conflicts`; reviews of the same card keep the earlier one. Writes that apply remote data set `sync_state.applying` (`payloads::set_applying`); the triggers still bump versions and write tombstones then, but also record the resulting version in `sync_echoes`, and the desktop's push skips rows whose version is still an echo. That keeps pulled data from being pushed back while a desktop can still relay it to a phone that syncs with it. The desktop-only endpoints (`sync/local.rs`: connect, status, run, conflicts) 404 outside `AUTH_MODE=desktop`, and a background loop syncs every 10s when there are local changes, otherwise every minute.
- Desktop reach: the desktop server listens on `127.0.0.1:47821` (random if taken) so the extension can find it. Opt-in phone access (`server/src/lan.rs`) opens a second listener on the local network, HTTPS with a per-device self-signed certificate (`server/src/tls.rs`), that strips cookies and only accepts bearer tokens; the connect link carries the certificate fingerprint (`fp`) and sync clients pin it (`sync_remote.pinned_cert`, `Remote::pinned`); pairing tokens are marked `created_by = 'desktop-pairing'` and revoked when phone access is turned off. Desktop-only endpoints (`/api/desktop/*`, the `sync/local.rs` routes) need a real session, never a token. Per-device settings that must not sync (backup folder, phone access) live in the `device_settings` table.
- Revisions: `note_revisions` (migration 0005) is filled by the `note_revisions_before_update` trigger in `ensure.sql`: the pre-edit name/content is kept when the note's newest revision is over 10 minutes old, at most 50 per note, removed with the note. Revisions are per device (not synced, not in `sync_bases`) but are in `VACUUM INTO` backups; restoring (`notes/revisions.rs`) snapshots the current text first, then writes a normal edit that syncs.
- Attachments ([design](docs/plans/attachments-design.md)): PNG/JPEG/WebP/GIF/PDF stored as content-addressed blobs in SQLite (`attachment_blobs`) with per-note rows in `attachments` (`server/src/attachments.rs`, migration 0006). Type comes from magic bytes; notes reference files as `attachment:<uid>` links that clients resolve through authenticated `/api/attachments/{uid}/file` fetches (object URLs on web). Triggers in `ensure.sql` drop unreferenced blobs and a note's attachments when it is permanently deleted. Sync, orphan cleanup, export ZIP and mobile are still to do.
- Scheduling: each note stores its own `algorithm` (`sm2` or `fsrs`); new notes follow `Settings.default_algorithm` (defaults to `fsrs`).
- Review status: a note is In review, Paused (`paused_at` set), or Note only (`in_review` false: no pending reminder, never paused, past reviews kept). Move notes between them with `remove_from_review` / `add_to_review` in `server/src/notes/bulk.rs` so that holds. Labels and the `active | paused | note-only` values live in `frontend/src/notes/reviewStatus.ts`, shared with mobile.
- Command palette: `frontend/src/command-palette/`, opened with `Cmd/Ctrl+/` (and `Cmd/Ctrl+K` outside the editor, where it would clash with insert-link). Pages add context commands with `usePageCommands` (memoize the array). Search results live under `["notes", "search", q]`, so existing `["notes"]` invalidations keep them fresh.
- Query cache families: `["notes"]`, `["due-notes"]`, `["trashed-notes"]`, `["projects"]`, `["tags"]`, `["auth-status"]`, `["system"]`, `["sync"]` (desktop only: status and conflicts; `SyncWatcher` refreshes every family when a background sync pulls changes). Mutations invalidate by prefix.

## URL state on the notes list

- Everything that shapes `/notes` (tag, project, date as `yyyy-MM-dd`, `q`, status, sort, order, page, pageSize) is a search param validated by `notesSearchSchema` in `frontend/src/notes/notes-list/notesSearch.ts`. New list state goes into that schema, not `useState`, so back/forward and reload restore it.
- Zod v4 schemas are passed to `validateSearch` directly, each field ending in `.catch(undefined)`; `@tanstack/zod-adapter` is not used.
- Update params with `search: (prev) => ({ ...prev, ... })` so other filters survive.
- A search middleware on the route drops `page` whenever a filter changes.
- "Back to list" targets (the note page's All Notes link, the redirect after delete) use `lastNotesSearch()`. The sidebar entry stays unfiltered.
- Per-viewer display preferences (grid/table view mode) live in localStorage, not the URL.
